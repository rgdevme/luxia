# Documentation authoring

Follow these conventions whenever you create or edit documentation under the
project's docs root (the `docs.root` configured in `agnos.json`, default `.docs`).

## Mandatory

- Read and follow the `okf-authoring` skill before applying this skill. Do not by-pass it.
- Treat this skill as rules-specific policy layered on top of `okf-authoring`.
- Use a documentation-specific `type`, such as `Technical Doc`, `Playbook`, or `BigQuery Table`.
- Use conventional body sections from `okf-authoring` when their content applies.

## Reserved files

- `index.md` is autogenerated by `agnos docs`. Never edit it by hand.
- `log.md` is a reserved change history. Do not list it as a concept document.

## Documenting conventions

- If a task changes how a system works (auth flow, data model, API pattern subscription logic, etc.), update the relevant file in `<docs-root>/technical/`.
- If a task introduces an architectural decision (a new pattern, library, or architectural approach), document it in `<docs-root>/technical-decisions`.
- Do not update business, product, or design docs automatically. Surface gaps and let the user decide.
- If a task implies an undocumented decision in any of these areas, flag it at the end of your response:
  > Doc gap detected: [Decision summary]. Consider updating
  > `<docs-root>/[section]/[file].md`.

## Change log

If `<docs-root>/log.md` exists, maintain it after every documentation change:

- Group entries under an ISO 8601 date heading (`## 2026-06-30`), newest first.
- Add one entry per change describing what changed and why.
- Link affected documents with Markdown links.
- Append to today's heading if it already exists.
- Do not create duplicate date headings.

Example:

```markdown
# Log

## 2026-06-30

- Documented the new auth flow in [Auth](technical/auth.md) after switching to
  token rotation.
- Removed the legacy session doc; the pattern no longer exists.
```
